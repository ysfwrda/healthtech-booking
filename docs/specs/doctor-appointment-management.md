# Design: Doctor appointment management, availability and vacations

Status: approved for issue #101 and the user's request of 2026-10-22: passed design-reviewer after revisions for its confirmed findings (the last round's blocking finding was revised for but not re-reviewed, per the skill's stop rule); the user approved its "Ask first" items on 2026-10-22 and decided that removal of doctors and patients is left to #116. Records the design at approval; the code, README and ADRs are the current state.

## Task
Issue #101 ("Doctor appointment management, availability editing and separate doctor/patient UIs"), and the user's request:

> Doctor should be able to manage appointments, therefore appointments booked by patients need to be set in status pending before doctor confirms them (for seeded doctors they should be confirmed automatically).
> Doctor should be able to confirm appointment, cancel it or change it. In all cases a notification is sent to the patient (notification service). Doctors should also be able to manage their availability and enter vacations.
> Implementation should be on two PRs, one for frontend and one for backend.

Out of scope: notifying the doctor about new bookings or patient-side changes (issue #101 mentions it as a problem; the user's request lists patient notifications only). The doctor finds new `PENDING` bookings in the list. Events already carry `doctorId`, so a doctor notification can be added later in notification-service.

Clarified with the user: a doctor's change applies directly (no patient acceptance, status unchanged); the 48-hour notice rule does not apply to the doctor; vacations are date ranges (inclusive, whole days). When the doctor changes hours or enters a vacation that affects already-booked appointments, the change is always saved; the affected appointments are flagged and the patients notified (user decision, 2026-10-22, replacing an earlier "reject with 409" decision).

## Approach
**Booking status.** `bookAppointment` stores `PENDING`, or `CONFIRMED` when the doctor's read-model row has `autoConfirmBookings = true`. `doctor.registered` gets a field `autoConfirmBookings`: `true` from `DoctorSeeder`, `false` from registration. `appointment.booked` is published as today in both cases. `PENDING` holds the slot (the partial unique index only excludes `CANCELLED`). Status machine: `PENDING -> CONFIRMED`, `PENDING|CONFIRMED -> CANCELLED`, nothing else; no expiry of old `PENDING` rows. A patient change never alters the status.

**Doctor appointment actions (appointment-service).** New `DoctorAppointmentController` under `/api/appointments/doctor`, role `DOCTOR`; the doctor id is the token subject and must equal `appointment.doctorId` (else 403). All use `findByIdForUpdate`.
- `GET /api/appointments/doctor?from=&to=&status=` (dates inclusive, all optional, `status` repeatable) -> `DoctorAppointmentResponse` (appointment fields + `conflictReason` + `patientName`, `patientEmail` from `ValidPatient`), ordered by date.
- `PUT .../{id}/confirm`: `PENDING` -> `CONFIRMED`, publishes `appointment.confirmed`. Already `CONFIRMED`: no-op, no event. `CANCELLED`, or flagged with a `conflictReason`: 409 `Appointment Not Confirmable` (a flagged appointment no longer fits the doctor's availability; the doctor changes its time, which clears the flag, or cancels it).
- `PUT .../{id}/cancel`: idempotent, 200, any non-cancelled appointment whatever its start time, no notice rule; publishes `appointment.cancelled` with `cancelledBy = DOCTOR`.
- `PATCH .../{id}`: `DoctorAppointmentUpdateRequest` (`type?`, `dateTime?`, at least one; there is no `notes`, so a doctor cannot rewrite the patient's own notes and every accepted doctor change is one the patient is told about). `CANCELLED` -> 409 `Appointment Not Changeable`. No notice rule. A new time must pass every `BookingRule` (so it is in the future, in hours, not on vacation). Status unchanged. Publishes `appointment.changed` with `changedBy = DOCTOR` when type or time differs from the stored value (a request that changes nothing publishes nothing, as for patients).
The patient and doctor update paths share one private method in `AppointmentService`; they differ in the ownership check, the notice check and `changedBy`.

**Availability and vacations (doctor-service owns the data).** Opening hours stay in doctor-service; vacations are added there (`doctor_vacation (id, doctor_id, start_date, end_date)`). Endpoints, role `DOCTOR`, doctor = token subject:
- `GET /api/doctors/me/availability` -> `{openingHours, vacations}`; a vacation is `{id, startDate, endDate}`. Vacations that ended before today (by the service's clock, which is the system default zone like the rest of the code; one clinic zone is #114) are not returned and not included in the event snapshot, so the payload stays bounded. `PUT .../opening-hours` answers 200 with the same availability body; `POST .../vacations` answers 201 with the created vacation.
- `PUT /api/doctors/me/availability/opening-hours`: replaces the weekly blocks; validated by the existing `ValidOpeningHours` (half-hour grid, end after start, no overlaps). An empty set is allowed (the doctor then offers no slots).
- `POST /api/doctors/me/availability/vacations` (`{startDate, endDate}`, `startDate <= endDate`, `endDate` not before today; overlapping ranges allowed) -> 201. `DELETE .../vacations/{id}` -> 204 (own vacations only; another doctor's id -> 404).
Each write loads the doctor row `FOR UPDATE` (so concurrent edits are serialized), saves, and in the same transaction publishes `doctor.availability-updated` (outbox) with the full snapshot: `{eventId, doctorId, openingHours, vacations, version}`; `version` is the new column `doctors.availability_version`, incremented by one under the row lock, so the versions of one doctor are consecutive and ordered by construction. The change is never refused because of existing appointments.

**Reacting to a change (appointment-service).** The read model `ValidDoctor` gains `vacations` (element collection), `autoConfirmBookings` and `availabilityVersion`. A new listener on `doctor.availability-updated` runs two steps, in this order, and never holds the `ValidDoctor` lock while it touches appointments (so it cannot deadlock with the patient/doctor PATCH, which lock the appointment first and then read the doctor `FOR SHARE`):
1. **Apply (own transaction).** Load the `ValidDoctor` row `FOR UPDATE`; if `version` is greater than `availabilityVersion`, replace hours and vacations and store the version; otherwise change nothing. Commit.
2. **Re-evaluate (always runs, also for a stale or redelivered event, because it is idempotent and reads the current model).** Query the ids of the doctor's non-cancelled appointments with `dateTime >= now`. For each id, in its own short transaction: `findByIdForUpdate` (the appointment lock, no doctor lock held), skip it if it is now cancelled, evaluate it against the current read model, and set `conflictReason` to `OUTSIDE_OPENING_HOURS` or `DOCTOR_VACATION` when it no longer fits (vacation wins if both) or to null when it fits again. When it goes from null (or a different reason) to a reason, publish `appointment.reschedule-required {eventId, appointmentId, patientId, doctorId, dateTime, reason, detectedAt}` in that transaction. Clearing and an unchanged flag publish nothing, so a redelivery notifies nobody twice. A failure for one appointment is caught and logged with its id and does not stop the others; after the loop, if any failed, the listener throws so the record is retried. If the process crashes between the two steps or part-way through step 2, the offset is not committed; the redelivery skips step 1 and finishes step 2. appointment-service uses Spring Kafka's default error handling (a few immediate retries, then the record is logged and skipped, ADR-009 "not implemented"): a persistent failure leaves the appointments it could not process unflagged until the doctor's next availability change or until they are evaluated again by a later event. This is accepted and stated in the README; a retry policy and dead-letter topic remain the ADR-009 Phase 3 work.
Booking and time changes read the `ValidDoctor` row `FOR SHARE` (3s cap, the existing 503 `Appointment Busy` handler) when they run the rules. Step 1's `FOR UPDATE` waits for such a transaction to commit, so a booking that commits first is already visible to step 2's query, and a later booking sees the new hours. Appointments in the past are never flagged.
`conflictReason` is a nullable column on `appointments` and is returned in `AppointmentResponse` and `DoctorAppointmentResponse`. A flagged appointment stays `PENDING`/`CONFIRMED`. The patient resolves it by changing the time (PATCH) or cancelling; the 48-hour notice check is waived while `conflictReason` is set (the doctor caused it). A successful time change runs the rules and clears the flag. The doctor can cancel or change it as for any appointment.
New rule `NotOnVacationRule` (`BookingRule`, `@Order(4)`) rejects a slot on a vacation day with 400 `Slot On Vacation`; `AvailabilityService` returns no slots on vacation days.
`doctor.registered` (appointment-service consumer): unknown id creates the row with names, hours and the flag; existing id loads the row `FOR UPDATE` (the same lock as step 1, so the two listeners, which run on different threads, cannot interleave) and updates names and `autoConfirmBookings` only, never hours, vacations or `availabilityVersion`, so it cannot undo availability edits or regress the version.

**Notifications (notification-service).** New events `appointment.confirmed` (`{eventId, appointmentId, patientId, doctorId, dateTime, confirmedAt}`) and `appointment.reschedule-required`, with `NotificationType.APPOINTMENT_CONFIRMED` ("Appointment confirmed for <dateTime>") and `APPOINTMENT_RESCHEDULE_REQUIRED` ("Your doctor is no longer available on <dateTime>, please reschedule or cancel"). `AppointmentCancelled` and `AppointmentChanged` get an optional `cancelledBy` / `changedBy` (`PATIENT` | `DOCTOR`, absent = `PATIENT`); for `DOCTOR` the message ends with " by your doctor". The existing listener/factory/`record` mechanism is reused.

**Frontend (second PR).** Role-specific shell: `Layout` shows patient links only to a patient session and doctor links only to a doctor session; separate landing routes (`/` search for patients, `/doctor/appointments` for doctors); `RequireAuth` per role. Doctor pages: appointments (filter by date range/status; Confirm / Cancel / Change per row, reusing `ChangeAppointmentForm` and `SlotPicker`; rows with a `conflictReason` highlighted), availability (weekly hours editor; vacations add/remove; after saving, a notice that affected appointments were flagged and their patients notified). Patients see `PENDING` as "Awaiting confirmation" and a flagged appointment with a "Your doctor is no longer available, please reschedule or cancel" banner; the 400 `Slot On Vacation` is shown like other slot errors.

## Alternatives considered
- Reject an hours/vacation change that hits booked appointments (409): was the earlier design; it needs appointment data in doctor-service's write path, i.e. a sync call (against ADR-005/ADR-002) or moving ownership of the hours to appointment-service (new ADR, a doctor-service consumer, a duplicated validator). Replaced at the user's request.
- Auto-cancel affected appointments: destructive, patients lose appointments with no decision.
- A new status (e.g. `NEEDS_RESCHEDULING`) instead of a flag: the status machine would multiply (flagged + pending/confirmed); the flag is orthogonal.
- Doctor change puts the appointment back to a patient-acceptance state: rejected by the user.
- A separate `appointment.rejected` for a doctor declining a `PENDING` appointment: it is a cancel; `cancelledBy` carries the difference.
- Doctor endpoints in the existing `AppointmentController`: its authorization is patient-only; a separate controller/prefix keeps the role rule one `requestMatchers` line.
- Existing `valid_doctor` rows defaulting `autoConfirmBookings` to `true` instead of re-publishing for seeded doctors: simpler, but self-registered doctors in old dev databases would auto-confirm.

No new ADR.

## Hard-to-reverse decisions
- **Event payloads:** `doctor.registered` + `autoConfirmBookings`; new `doctor.availability-updated` (a full snapshot, so replace is idempotent and a lost event is healed by the next one); new `appointment.confirmed` and `appointment.reschedule-required`; optional `cancelledBy` / `changedBy`. All additive. ADR planned: no (same outbox/topic pattern as ADR-008; the README documents the topics).
- **Data model:** `appointments.conflict_reason` (nullable enum), `doctor_vacation` and `doctors.availability_version` in doctor-service, `valid_doctor.auto_confirm_bookings` / `availability_version` and a vacations collection table in appointment-service. ADR planned: no.
- **API shapes** (paths under `/api/appointments/doctor` and `/api/doctors/me`; `PUT` for state transitions as `PUT /{id}/cancel` today, `PATCH` for edits). ADR planned: no.
- **Flag, not status** for a conflicted appointment. ADR planned: no; the rule goes to the README.

## Contracts
- appointment-service, role `DOCTOR` (401 without token, 403 for a patient token or another doctor's resource; confirm, cancel and change can also answer 503 `Appointment Busy`, the list takes no lock):
  - `GET /api/appointments/doctor` (200; 400 on bad dates or `from > to`)
  - `PUT /api/appointments/doctor/{id}/confirm` (200; 404; 409 `Appointment Not Confirmable`)
  - `PUT /api/appointments/doctor/{id}/cancel` (200; 404)
  - `PATCH /api/appointments/doctor/{id}` (200; 400 validation, unaligned, outside hours, past, `Slot On Vacation`; 404; 409 slot taken or cancelled)
- doctor-service, role `DOCTOR` (401, 403 for a patient token):
  - `GET /api/doctors/me/availability` (200)
  - `PUT /api/doctors/me/availability/opening-hours` (200; 400; 404 if the doctor row is gone)
  - `POST /api/doctors/me/availability/vacations` (201; 400)
  - `DELETE /api/doctors/me/availability/vacations/{id}` (204; 404)
- Changed: `POST /api/appointments` returns status `PENDING` for non-auto-confirm doctors, 400 `Slot On Vacation`, and can answer 503 `Appointment Busy` (doctor-row lock); the patient `PATCH /api/appointments/{id}` can also answer 400 `Slot On Vacation` and 503, and skips the 48-hour check for a flagged appointment; `AppointmentResponse` gains `conflictReason`; `GET /api/availability` returns no slots on vacation days.
- Events: see Hard-to-reverse. New topics `appointment.confirmed`, `appointment.reschedule-required`, `doctor.availability-updated`.
- Schema: appointment-service Hibernate `update` adds `appointments.conflict_reason` (nullable), `valid_doctor.auto_confirm_bookings` with `@Column(columnDefinition = "boolean not null default false")` (so existing rows get `false`), `valid_doctor.availability_version` (nullable, null = none applied) and `valid_doctor_vacation`; doctor-service adds `doctor_vacation` and `doctors.availability_version` (`columnDefinition = "bigint not null default 0"`); notification-service none (its type check constraint is already dropped by its startup script). No `schema-postgresql.sql` change.
- Gateway: `/api/doctors/me/**` requires authentication before the public `GET /api/doctors/**` rule; routing and CORS are unchanged (to be confirmed for PUT/DELETE in implementation).
- Dependencies: none.

## Failure modes
- Kafka down or lagging: events go through the outbox. A late `doctor.availability-updated` delays the flagging and the scheduling restrictions in appointment-service (patients may book a slot the doctor has just removed until the event arrives; those bookings are flagged by the re-evaluation when it runs). The doctor's change itself is never delayed.
- Duplicate or reordered delivery: `availabilityVersion` guard in step 1 (an older or equal `version` changes nothing), step 2 is idempotent and flag transitions publish only on a change, so a duplicate notifies nobody; notification `event_id` unique index (ADR-009) covers the new notification events.
- Booking racing the event: see the locking paragraph above. The collections of `ValidDoctor` are loaded after the lock wait, not in the same statement as the lock. Lock timeout 3s -> 503 `Appointment Busy`, retry safe.
- `doctor.registered` (seeder re-publish) racing step 1 of the availability listener: both load the `ValidDoctor` row `FOR UPDATE`, so a full-row write by one cannot overwrite the other's `availabilityVersion` or collections (`ValidDoctor` has no `@Version`).
- Listener racing a patient/doctor action on one appointment: step 2 takes `findByIdForUpdate` and re-reads the status, so it cannot write a stale full-row update over a committed cancel or change (`Appointment` has no `@Version`); it holds no `ValidDoctor` lock then, so there is no lock cycle with PATCH. A step-2 failure rolls back only that appointment's transaction; the other appointments are still processed and the record is retried, and the finished appointments are unchanged by a repeat. Retries stop with the default handler's limit, after which the record is skipped and the remaining unflagged appointments wait for the next availability event (accepted, see step 2).
- Doctor missing from the read model when the event arrives (event before `doctor.registered`): the listener creates the row from the snapshot with `autoConfirmBookings = false`, names unset until `doctor.registered` arrives and fills them (that handler updates names/flag on an existing row).
- Doctor vs patient actions racing on one appointment: serialized by `findByIdForUpdate`; confirm after cancel -> 409.
- Doctor missing from the read model on booking/time change: 404 `Doctor Not Found`, as today.
- Existing databases: seeded doctors exist, so their flag is `false` after the column default; `DoctorSeeder` re-publishes `doctor.registered` for already-seeded doctors on every start and the consumer sets the flag.
- Rollback: appointment-service's old strict mapper would loop on the new `doctor.registered` field that doctor-service keeps publishing (ADR-009 "Poison pills"); the two services are rolled back together, which the README states.
- A time change to the appointment's own current time: unchanged (no event, flag unchanged).
- Doctor re-saves identical hours: the event is still published; the re-evaluation changes nothing and notifies nobody.

- ADR changes: ADR-005, ADR-008, ADR-009 as listed under "Fits the codebase"; no new ADR.
- Decisions I made that the user may overturn: when a flag is cleared (the doctor reverts the change) the patient gets no "all clear" notification; confirming a flagged appointment is refused (409); a listener failure that outlasts the default retries is accepted (no dead-letter); `autoConfirmBookings` lives only in the event and appointment-service's read model, set by the seeder on every start (storing it on doctor-service's `doctors` row would give it an owner and is the first step if a doctor-editable setting is added later); a patient change never alters the status; `PENDING` appointments never expire; an empty set of opening hours is allowed; the doctor may cancel, confirm or change any non-cancelled appointment regardless of its start time; the patient's 48-hour notice is waived for a flagged appointment; a flagged appointment keeps its status and slot until someone acts; the re-publish of `doctor.registered` for seeded doctors on every start (instead of defaulting old rows to `true`); the patient's "booked" notification reads the same for pending and auto-confirmed bookings (a `status` on `appointment.booked` can be added later).

## Departures from this note (recorded at implementation)
- The `appointment.confirmed` and `appointment.reschedule-required` payloads also carry `duration`, like the other appointment events.
- The doctor list answers 400 `Invalid Date Range` for `from` after `to`; doctor-service names its two new problems `Vacation Not Found` (404) and `Invalid Vacation` (400).
- The "clinic zone `Europe/Berlin`" is not set: both services use the system default zone, like the existing code (one clinic zone is #114).
- Outbox atomicity of the doctor-service availability writes (a rejected request publishes nothing) is asserted in `DoctorAvailabilityIntegrationTest`, not in doctor-service's `OutboxAtomicityIntegrationTest`; the listener's flag and its `appointment.reschedule-required` row are asserted together in `AvailabilityChangeIntegrationTest`. A step-2 failure leaving no row is covered by the unit test of the per-appointment isolation, not by an integration test.
- The `DoctorAppointmentSpecifications` filter replaces the single repository query the note implied.
- Known limits found in review and left as they are: a `doctor.registered` for a doctor the appointment service does not know builds the row without vacations (the next availability change fixes it), and an availability snapshot for an unknown doctor leaves the names empty until `doctor.registered` arrives, so a booking in that window carries "null null" as the doctor name.
